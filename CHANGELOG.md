Created a stratified random split (6236 train / 1559 test, seed 42) and a Bemis-Murcko scaffold split (6236 train / 1559 test, zero overlap) using a deterministic greedy bin-packing algorithm. Verified zero scaffold leakage and logged a natural class balance shift in the scaffold split (64.19% train / 60.94% test BBB+). Saved split index lists as `splits/random_split_indices.json`, `splits/scaffold_split_indices.json`, and generated split metadata JSON and markdown reports.

Trained 18 primary classification models (Logistic Regression, Random Forest, XGBoost across Descriptors, Fingerprints, and Combined representations) and 2 baseline majority class runs. Locked global seed at 42. Enforced strict leakage-free preprocessing pipelines (e.g. scaling descriptors part only in combined features). Saved predictions, metrics, feature importances, and model configurations in `results/` subdirectories. Populated metrics comparison tables, documented generalization gap drops, and logged initial descriptor importance values (TPSA and H-Bond Donors are the highest predictors).

Saved ROC curves, PR curves, confusion matrices, generalization gap bar plots, and feature importance bar plots under `results/figures/`. - **Post-Phase-13 Feature:** Added compound name search, since typing a raw SMILES string is not something most users know how to do. `GET /api/molecules/search?q=&limit=` (`backend/app/routes/molecules.py`, `backend/app/services/molecule_search.py`) searches all 7,795 `compound_name` entries in the cleaned B3DB dataset (prefix matches ranked first), returning `{name, smiles}` pairs; degrades to an empty result set rather than crashing if the source CSV is unavailable. Investigated data quality first: ~1,100 of 7,795 rows have no name at all, common drugs like Aspirin/Paracetamol aren't present under those names, and some names (e.g. "morphine", 29 matches) map to multiple, sometimes conflicting SMILES across the merged source studies. Rather than picking one silently, every distinct (name, SMILES) pair is returned so the new `MoleculeSearchInput` typeahead component (wired into `SmilesInput.tsx` above the existing textarea) shows the raw SMILES under each name and explicitly tells users to verify via the rendered structure. - **Post-Phase-13 Fixes (full-project review):** Fixed six issues found during a full-project audit, all verified by reproduction before fixing: (1) **BOM handling bug** — CSV uploads with a leading UTF-8 byte-order-mark (which Excel's "CSV UTF-8" export always adds) were rejected with "Missing required SMILES column" even with a valid column, because `'﻿smiles' != 'smiles'`; fixed by decoding with `utf-8-sig` in `backend/app/routes/batch.py`. (2) **CSV formula injection** on batch export — `BatchScreenerPage.tsx`'s `escape()` didn't neutralize cells starting with `=`/`+`/`-`/`@`, which Excel/Sheets can interpret as formulas on reopen; fixed by prefixing a `'` before existing quote-escaping. (3) **Race condition** in the new `MoleculeSearchInput` — debounced but uncancelled fetches could let a stale response overwrite a newer one; fixed with `AbortController` + a request-sequence guard. (4) **Unbounded upload buffering** — `batch.py` read the entire file into memory before checking the 5MB limit; changed to chunked reads that reject as soon as the limit is crossed. (5) **No SMILES length cap** — added a 1000-character guard (3x the longest real SMILES in the training set, 338 chars) in `validate_and_parse_smiles()` (`backend/app/services/molecule.py`), shared by `/predict`, `/predict/batch`, and `/explain`. (6) **Unpinned ML dependencies** — `backend/requirements.txt` used `>=` with no upper bound on `scikit-learn`/`numpy`, risking a future `pip install` breaking `joblib` deserialization of the frozen model (which scikit-learn does not guarantee across versions); repinned every dependency to the exact version already verified working in this venv (matches `production_metadata.json`'s recorded `environment_versions`). Also addressed from the same audit: deduplicated the nav markup in `AppShell.tsx` into a single `NAV_ITEMS` array (was defined twice, sidebar + mobile header), added a top-level `ErrorBoundary` (`App.tsx`) so a rendering crash in one tab shows a recoverable message instead of a blank white screen, added keyboard navigation (arrow keys + Enter + Escape) and ARIA combobox/listbox roles to `MoleculeSearchInput`, and added a root `.gitignore` (previously only `frontend/.gitignore` existed). - **Post-Phase-13 Enhancements (applicability domain, statistical rigor, batch/UI improvements):** Six further improvements from a deeper project audit, each verified concretely (numbers reproduced, not estimated) before implementing.
  - **Statistical significance of the model selection.** `backend/scripts/statistical_significance.py` runs McNemar's exact test and a paired bootstrap (2,000 resamples, seed=42) on the already-saved Phase 5 scaffold predictions (`results/predictions/rf_descriptors_scaffold_predictions.csv` vs. `xgb_combined_scaffold_predictions.csv`) — no retraining. Finding: the accuracy gap between RF+Descriptors and XGBoost+Combined (74.47% vs. 72.80%) is **not** significant (McNemar p=0.102), but the Macro F1 gap **is** (+0.0374, 95% CI [+0.0154, +0.0592], excludes zero) — this project's stated primary metric under class imbalance. Wrote `results/analysis/statistical_significance.md`/`.json` and updated `results/analysis/final_model_recommendation.md` and `docs/REPORT_OUTLINE.md` §11.3 to state the selection rationale rests on Macro F1, not accuracy.
  - **Applicability domain (nearest-neighbor similarity).** New `backend/app/services/applicability_domain.py` loads `features/fingerprints.npz` (row-aligned with the cleaned dataset) once and answers Tanimoto nearest-neighbor queries (~14ms over all 7,795 training molecules), reusing the authoritative Phase 2 fingerprint function (`src/features/fingerprints.py`) so query fingerprints match training fingerprints exactly. Added to `POST /api/predict`'s response as `applicability_domain: {max_similarity, nearest_neighbors}` — the model itself has no notion of "out of distribution" and scores novel structures with the same apparent certainty as familiar ones, so this flags when a prediction is extrapolating. New `ApplicabilityDomainCard` frontend component shows the similarity score and up to 5 nearest training-set molecules with their real BBB label. Caught and fixed a key-name mismatch (`neighbors` vs. schema's `nearest_neighbors`) that Pydantic silently swallowed via its default extra-field handling, discovered only by checking the live response, not just schema validation passing.
  - **Tree-vote uncertainty.** `predictor.py` now also computes the standard deviation and IQR of all 250 individual tree probability votes (`model.estimators_`) — free, since the trees are already in memory — surfaced in the same `ApplicabilityDomainCard` as "tree vote spread." Explicitly documented as informational only, consistent with this project's existing rule to never call model output a "confidence score."
  - **Sortable batch results.** `BatchScreenerPage.tsx` table headers (Row, BBB+ Probability, MW, LogP) are now clickable and sort the filtered result set before pagination, with error rows always sorting to the end regardless of direction — previously a 5,000-row batch could only be filtered/paginated, with no way to surface the highest-probability hits.
  - **Evaluation figures in the Performance tab.** New `GET /static/figures/<name>.png` static mount (`RESULTS_FIGURES_PATH`, conditional like the Phase 12 frontend mount) serves the existing Phase 5 PNGs (ROC/PR curves, confusion matrix, generalization gap) read-only; new `EvaluationFigures` component displays them with a graceful "Figure unavailable" fallback on load failure. Previously the Performance tab showed only numbers despite these plots already existing on disk.
  - **Dockerfile updated** to copy `backend/data/processed`, `features/fingerprints.npz`, and `results/figures` (previously excluded as "training-only") since three of today's features now depend on them at runtime; `.dockerignore` narrowed from blanket `features`/`results` exclusions to per-file exclusions so the needed files remain in the build context.
  - Verified: 45 backend pytest cases passing (42 prior + 3 new: exact-match applicability domain, tree uncertainty bounds, determinism), 29 frontend Vitest cases passing (26 prior + 3 new: applicability domain card rendering, batch sort ordering, evaluation figure fallback), `npm run build` succeeding, and all of the above re-verified live against a running backend/frontend (Caffeine's applicability domain, sort ordering on a real 4-row batch, and all 4 figures loading with nonzero `naturalWidth`). No live `docker build` was run (same standing scope decision as Phase 12).
- **Post-Phase-13 Fix: common drug name search gaps.** Checked exact-structure matches (not just name matches) for the app's own reference drugs and found the raw B3DB data actively misleads on two of them: searching "aspirin" or "paracetamol" returned zero results (they're filed under CAS number `50-78-2` and the synonym "acetaminophen" respectively), and searching "caffeine" returned a *wrong* structure — the string "caffeine" in the raw data is attached to an unrelated compound, while the real caffeine sits under CAS `58-08-2`. Added a small `VERIFIED_ALIASES` table to `backend/app/services/molecule_search.py` (Caffeine, Aspirin, Ibuprofen, Paracetamol, Acetaminophen), using the same SMILES already trusted elsewhere in this app (the four example buttons), canonicalized once via RDKit at import time so exact-string dedup against raw dataset matches works correctly. Verified aliases now rank first and are marked `"verified": true` in the API response and with a "Verified" badge in `MoleculeSearchInput.tsx`; the raw (sometimes mislabeled) dataset entries are still shown alongside them rather than hidden, preserving this feature's transparency design. Added `verified: bool` to the `MoleculeSearchResult` schema. Updated two backend tests that had asserted the *old*, gap-having behavior (one literally titled "documents the known data-quality gap") to instead assert the fix. Verified: 45 backend pytest cases passing, 30 frontend Vitest cases passing (29 prior + 1 new: verified badge rendering), `npm run build` succeeding, and both the Aspirin fix and the Caffeine dual-result display re-verified live via direct API calls and in the running browser UI.
- **Post-Phase-13 Feature: automatic duplicate-name consistency detection.** Prompted by a user question ("I searched azithromycin and found so many, idk which to see") — checking manually confirmed 4 of 6 same-named "azithromycin" results were genuine stereoisomers of the real drug (Tanimoto similarity 0.86-1.0 to each other) while 1 was a completely unrelated small molecule mislabeled in the source data (similarity 0.08), the same pattern already seen with morphine. Rather than asking users to eyeball SMILES strings, `MoleculeSearchService._annotate_group_consistency()` (`backend/app/services/molecule_search.py`) now computes this automatically at load time: for every compound_name shared by 2+ entries, pairwise Morgan fingerprint Tanimoto similarity (reusing `features/fingerprints.npz`, the same row-aligned matrix used for applicability domain) determines whether each entry is a plausible variant of its same-named siblings (`group_consistent: true`) or a probable data error (`group_consistent: false`, threshold 0.5, chosen from the measured 0.86-1.0 vs. 0.08 gap). `null` when a name has nothing to compare against. Added `group_consistent: bool | None` to the `MoleculeSearchResult` schema, and a red "Differs from others" badge in `MoleculeSearchInput.tsx` shown only on flagged entries. One-time cost: 121ms on the first search of the app's life (annotates all 7,795 entries), <1ms after, since results are cached in the same singleton. This also surfaced a previously-undocumented case: 2 "apomorphine" entries in B3DB that are themselves structurally inconsistent with each other. Verified: 47 backend pytest cases passing (45 prior + 2 new: inconsistent-flag detection on morphine, null-for-unique-names on ibuprofen), 31 frontend Vitest cases passing (30 prior + 1 new: warning badge rendering), `npm run build` succeeding, and the exact azithromycin/morphine cases discussed with the user re-verified live via direct API calls and in the running browser UI.
